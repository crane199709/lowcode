# 打印模板用声明式 JSON DSL，服务端生成的 HTML 是唯一排版权威

打印模板必须同时产出 PDF、编辑期预览和热敏位图三类结果，如果每类各实现一次排版，就会出现"预览好看、打出来错位"。因此模板存成受控的声明式 JSON（文档模板 = 页面 + 区块流 + 声明式表格，标签模板 = 毫米绝对坐标 + 元素白名单），由服务端 Java 生成一份自包含 HTML（内联 CSS、图片转 `data:` URI），前端预览直接在 `<iframe>` 里加载它，PDF 与位图都由同一份 HTML 经无头 Chromium 产出。放弃自由 HTML/CSS 模板是因为它无法做结构校验、无法派生热敏指令、无法按字段收敛权限；放弃纯 Java PDF 库是因为中文、跨页表格与覆盖层会退回手写排版；放弃前端为权威是因为服务端归档与批量产物没有浏览器。也不再引入 icube 那种 `--dump-dom` + JS 测量阶段：跨页表头用 `thead { display: table-header-group }`、行用 `break-inside: avoid` 即可，代价是一期不支持正文内的动态页码（`page` / `total` 只允许出现在页眉页脚），这是刻意接受的范围收缩。

## Considered Options

- **自由 HTML/CSS 模板 + 插值**：所见即所得最直接，但模板变成不可校验的字符串，热敏指令与字段级权限都无从谈起。
- **纯 Java PDF 库（OpenPDF / iText）自排**：运行时轻，但中文断行、跨页表格、水印平铺都要自己实现，等于重写一个排版引擎。
- **前端渲染为权威，服务端不产 PDF**：最省服务端资源，但归档、批量打印与无浏览器场景全部失效。
- **icube 的做法（Java 生成 HTML + 表格用 JS 测量）**：能力对齐，但多一个 CSP 哈希白名单脚本执行阶段，排查成本高，且正文页码以外没有额外收益。

## Consequences

- 编辑器画布只能是服务端 HTML 的可编辑映射，前端不能自由发挥布局。
- 文档正文只能是区块流，表格不接受任意单元格合并；需要复杂版式只能拆成多个区块或改用标签模板。
- 渲染器必须按快照里的 `schemaVersion` 分派并长期保留旧版本，否则历史修订无法重印。
- 页眉页脚受 Chromium 页眉页脚模板的能力限制（文本、页码、图片、对齐，不能放表格），编辑器必须同样限制。
